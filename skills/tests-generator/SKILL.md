## Overview

This skill generates tests for existing code. It:

- Detects the project's testing framework and follows its conventions
- Generates tests covering happy paths, edge cases, and error paths
- Follows the Arrange → Act → Assert (AAA) pattern
- Suggests test names that clearly describe the scenario being tested

Use this skill when asked to **generate tests** for a file, function, class, or module.

---

## Framework detection

Before generating tests, identify the testing framework from the project:

| Language | Look for | Framework examples |
|----------|----------|--------------------|
| TypeScript/JavaScript | `package.json` `devDependencies` | Jest, Vitest, Mocha, Jasmine |
| Python | `requirements*.txt`, `pyproject.toml`, `setup.cfg` | pytest, unittest |
| C# | `*.csproj` references | xUnit, NUnit, MSTest |
| Go | `*_test.go` existing files | `testing` package, testify |
| Java | `pom.xml` or `build.gradle` | JUnit 5, TestNG |

If no framework is detected, default to the most common for the language (e.g., Jest for TypeScript, pytest for Python, xUnit for C#).

## Test structure conventions

### Naming
- Test file: `<source-file>.test.<ext>` or `<source-file>_test.<ext>` — match project conventions
- Test group: describes the unit under test (class name, module name, or function name)
- Test case: describes the scenario in natural language

Good test name examples:
- `"should return 401 when no authorization header is provided"`
- `"returns empty array when input list is empty"`
- `"throws ArgumentNullException when userId is null"`

### Structure (AAA pattern)
```
// Arrange
const input = ...
const expected = ...

// Act
const result = await myFunction(input)

// Assert
expect(result).toEqual(expected)
```

## Coverage targets

For every public function or method, generate tests for:

1. **Happy path** — normal expected usage
2. **Boundary values** — empty string, zero, min/max integer, empty collection
3. **Null/undefined inputs** — verify graceful handling or appropriate error
4. **Error paths** — invalid input, thrown exceptions, rejected promises
5. **Side effects** — verify that expected side effects occur (database writes, event emissions)

---

## Mocking guidelines

- Mock all external dependencies: databases, HTTP clients, file system, time
- Use the project's existing mocking library (Jest mocks, pytest monkeypatch, Moq, etc.)
- Avoid real network calls or file I/O in unit tests
- For integration tests, use real dependencies or containerized equivalents (e.g., testcontainers)

---

## Output format

Return a complete test file, ready to save. Include:

1. Comment header: `// Generated by GitHub Copilot — review before committing.`
2. All necessary imports
3. One describe/test class block per source unit
4. Clear test names following the conventions above

## Usage patterns

### Pattern 1: Generate tests for a file

> "Generate unit tests for #file:src/services/userService.ts"

### Pattern 2: Generate tests for a selection

> "Write tests for this function: #selection"

### Pattern 3: Improve existing test coverage

> "Review the test file #file:tests/auth.test.ts and suggest missing test cases for #file:src/auth.ts"

---

## Constraints

- Do **not** modify the source file.
- Do **not** introduce a new testing library if one already exists in the project.
- Keep tests independent — each test should set up and tear down its own state.
- Prefer explicit assertions over snapshot testing unless the project already uses snapshots.
